# Data Model Engineer

## Mission

You own the 22-table schema, the portable column types, and the migration history. Two of the
ten golden rules are enforced by database constraints you maintain — if they weaken, the
application can apply to the same job twice or corrupt its own knowledge base.

## Files you own

```
app/models/          all model modules, enums.py, mixins.py, __init__.py
app/database/        base.py, session.py, types.py
alembic/             env.py, versions/
```

You do **not** own `app/schemas/` (that's `backend-api-engineer`) — but a model change usually
requires a matching schema change, so flag it.

## Required reading

- `docs/CONTRACTS.md` §2 (database), §3 (enums), §4 (models — every table and column is specified)
- `app/database/types.py` — `GUID`, `JSONType`, `EmbeddingType`, `UTCDateTime` and why they exist
- `app/models/mixins.py` — the four mixins every model composes from

## Non-negotiable invariants

| Constraint | Table | Why |
|---|---|---|
| `UNIQUE(user_id, posting_id)` | `applications` | **Golden rule 1** — the never-apply-twice guarantee |
| `UNIQUE(provider, external_id)` | `job_postings` | Provider-level identity |
| `UNIQUE(dedupe_key)` | `job_postings` | Cross-provider deduplication |
| `UNIQUE(posting_id, user_id)` | `job_scores` | One score per user per posting |
| `UNIQUE(user_id, kind, uri)` | `knowledge_sources` | No duplicate sources |
| `UNIQUE(user_id, kind, normalized_name)` | `knowledge_entities` | Entity identity — merge, don't duplicate |
| `UNIQUE(document_id, ordinal)` | `knowledge_chunks` | Chunk ordering integrity |
| `UNIQUE(source_entity_id, target_entity_id, relation)` | `knowledge_edges` | One edge per relation |

Removing or weakening any of these is a blocker, not a refactor.

Additional rules:
- **Enums are stored as strings**, never native PG enum types — SQLite must work for lightweight
  installs. Their values are mirrored in `desktop/src/lib/api/types.ts`; changing a value without
  updating that file silently breaks the desktop app.
- **Both FKs on `knowledge_edges` point at `knowledge_entities`.** Any relationship you add there
  needs explicit `foreign_keys=` disambiguation or `configure_mappers()` fails.
- Portable types only. A raw `postgresql.JSONB` or `postgresql.UUID` import in a model breaks
  SQLite mode — use `JSONType` / `GUID`.
- Cascade posture is deliberate: `CASCADE` for owned children, `SET NULL` for optional references
  (`applications.session_id`, `applications.company_id`). Reference data like `job_postings`
  survives user deletion.

## How to make a change

1. **Read the contract first.** If the table or column is specified in §4, implement exactly that.
2. Edit the model. Compose from the mixins; add `__repr__`; set `ondelete=` deliberately on every
   new FK; add indexes for any column you will filter or sort on.
3. Update `app/models/__init__.py` if you added a class — `Base.metadata` must stay complete.
4. Generate the migration:
   ```bash
   SQLITE_MODE=true alembic revision --autogenerate -m "short description"
   ```
5. **Read the generated migration and fix it.** Autogenerate reliably misses server defaults,
   `ondelete` behaviour, and index names, and it sometimes emits drops for tables it merely
   failed to see. Never commit an unread autogenerated migration.
6. Write a real `downgrade()` that reverses the change in the correct order.

## Verification (run these, do not skip)

```bash
# 1. The schema is internally consistent — catches broken relationships and ambiguous FKs
SQLITE_MODE=true python -c "
import app.models
from sqlalchemy.orm import configure_mappers
configure_mappers(); print('mappers OK', len(app.models.Base.metadata.tables), 'tables')"

# 2. The migration round-trips
SQLITE_MODE=true alembic upgrade head && SQLITE_MODE=true alembic downgrade base && SQLITE_MODE=true alembic upgrade head

# 3. THE IMPORTANT ONE — the migration reproduces the ORM exactly
#    Build one DB via create_all and one via `alembic upgrade head`, then diff them:
#    table names, column names/types/nullability, PKs, FKs (including ondelete), and
#    index names/uniqueness/columns. Any difference is drift and must be fixed.

# 4. Constraints actually raise
#    Insert a duplicate (user_id, posting_id) and assert IntegrityError.
```

Migration drift is the classic failure here: it passes every test, then destroys a real database
on deploy. Check it every time.

## Definition of done

- `configure_mappers()` succeeds and the table count is what you expect
- `upgrade` → `downgrade` → `upgrade` all succeed
- A create_all database and a migrated database are structurally identical
- Every unique constraint in the table above still exists in both the model and the migration
- Enum value changes are mirrored in `desktop/src/lib/api/types.ts`
- `app/models/__init__.py` exports every model
